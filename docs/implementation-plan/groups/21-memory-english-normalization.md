# Группа 21 — English normalization of durable memory (post-v0)

Третья группа, открытая после закрытия `T00–T17` (`G17: PASS`) по явному продуктовому решению —
`docs/adr/0010-memory-english-normalization.md`. Не переоткрывает ни один гейт `G00–G20`. Цель:
текст durable-записи приводится к английскому локальной генеративной моделью, которая в продукте
уже есть, и в вектор уходит именно английский вариант; канонический `memory_entry.text` при этом
не меняется никогда. Перевод текста запроса в эту группу **не входит** — он отложен до честного
замера (`T21-10`).

Ссылки: ADR-0010; ADR-0006 (рантайм локального генератора); spec 03 §1.4 `[FIXED]` (нет writable
cross-DB `ATTACH`), §2.5; spec 08 §3 `[FIXED]` (текст меняется только через `edit`/audit), §4
`[FIXED]` (`local_only` → локальный генератор), §5, §6 `[FIXED pipeline]` + as-built X-010/X-011;
spec 10 §3; spec 12 §2/§4 `[FIXED]` (untrusted-текст, purge); spec 14 §7;
`crates/store/src/memory/{mod,entry,op}.rs`; `crates/store/src/{subjects,cache/embedding}.rs`;
`crates/memory/src/recall/{pipeline,dense,lexical}.rs`; `crates/embed/src/{backfill,gen_pool,contract}.rs`;
`crates/local-rag/src/daemon/{lifecycle,jobs,idle,consolidation_trigger}.rs`;
`crates/xtask/src/memory_recall_bench/`; D-067, D-068.

Формат карточек — по `TASK-TEMPLATE.md`, структура группы — как в группах 18/20. Один таск —
одна итерация — один коммит.

## Диагноз (контекст для исполнителя — прочитать до начала)

1. **Связь «запись ↔ вектор» — вычисляемый хэш, а не FK.** `subject_memory_entry(memory_id, text)`
   (`crates/core/src/identity/domain.rs:230`) считается независимо в трёх местах:
   `crates/store/src/subjects.rs:270` (что ожидается от backfill'а),
   `crates/embed/src/backfill.rs:703` (что реально эмбеддится),
   `crates/memory/src/recall/dense.rs:211` (что ищется в кэше). Стоит определениям разойтись —
   dense-нога бесшумно вернёт ноль попаданий по затронутым записям. Это главный риск группы;
   `T21-02` покупает **структурную** гарантию, а не соглашение.
2. **`D-067`: dense-нога уже сегодня теряет кандидатов.** `dense_leg` ограничивает чтение кэша
   числом кандидатов (`dense.rs:198-201`), а ридер отдаёт строки по всем memory-записям стора —
   любых скоупов, любых состояний, плюс устаревшие хэши — `ORDER BY subject_hash LIMIT ?3`
   (`crates/store/src/cache/embedding.rs:307-320`). На живом сторе владельца: 86 строк кэша против
   44 кандидатов → ожидание ≈ 22 из 44. Нормализация удваивает число строк на запись, то есть
   усугубляет дефект. `D-067` обязан быть закрыт до `T21-05`.
3. **Memory-векторы пересчитываются только попутно с индексацией воркдерева.** Единственный
   продовый вызов `run_backfill` — `crates/local-rag/src/indexing/mod.rs:180` внутри
   `project_generation`. Стор без enrolled-проектов не пересчитает memory-векторы никогда, поэтому
   фоновый таск обязан сам закрывать вектор (`T21-05`), а не надеяться на цикл индексации.
4. **Единственный `GeneratorPool` на процесс.** `crates/local-rag/src/daemon/lifecycle.rs:504-506`,
   D-054: `LlamaBackend` — процессный синглтон, повторный `build_best_effort_pool` даёт
   `BackendAlreadyInitialized` и молчаливую деградацию до пустого пула на весь uptime. Новый
   потребитель обязан получить **клон того же `Arc`**.
5. **Уроки консолидации применяются превентивно.** D-050 (retry-storm на детерминированном сбое),
   D-057 (классификация mechanical/transient), D-024 (`JobGuard` только на время активного тика) —
   форма dead-letter, backoff и врезки воркера копируется, а не изобретается. Отдельно: отсутствие
   генератора — свойство окружения, а не записи, и обязано прерывать тик, а не помечать записи
   failed.
6. **`[FIXED]`-границы.** `memory_entry.text` неприкосновенен (08 §3); конвейер recall 08 §6 эта
   группа **не меняет** (меняется только текст, представленный вектором) — амендмент понадобился бы
   лишь `T21-10`; untrusted-текст, идущий в промпт переводчика, требует adversarial-тестов (12 §4).
7. **`D-068`: бенч недетерминирован.** `crates/xtask/src/memory_recall_bench/run.rs:275-276` минтит
   `memory_id` через `SystemUuidV7` при общем `created_at = 1_000`, поэтому тай-брейк
   `(score desc, created_at desc, memory_id)` решается случайным UUID. Из-за этого `store_en` и
   `both_en` — прогоны с побайтово идентичным входом на `en-en` — разошлись на одном запросе, и
   именно этот пол-балла составляет весь их overall-разрыв. Замер `T21-09` без `D-068` бессмыслен.

Порядок работ: регистрация (`T21-00`), затем блокирующий `D-067`, затем хранилище
(`T21-01` схема, `T21-02` эффективный текст), затем компоненты (`T21-03` детектор,
`T21-04` переводчик), затем проводка (`T21-05` запись, `T21-06` фоновый таск), затем поверхности
(`T21-07` privacy, `T21-08` наблюдаемость), затем измерение (`D-068`, `T21-09`), затем владельческое
решение по query-стороне (`T21-10`), затем гейт.

## D-067 — Dense-нога читает векторы по точным ключам, а не слепым `LIMIT`-сканом

- **Зависит от:** `T21-00` (только регистрацией строки в `DEVIATIONS.md`).
- **Спецификация:** spec 08 §6 (dense-нога); spec 03 §4.2.
- **Результат:** dense-нога получает вектор для **каждого** кандидата, у которого он есть в кэше,
  независимо от того, сколько посторонних memory-строк лежит в `embedding_cache`.
- **В scope:** новый ридер `embeddings_for_subjects(conn, subject_kind, representation_id, &[&str])`
  в `crates/store/src/cache/embedding.rs` (чанкованный `IN (…)` с запасом по лимиту параметров
  SQLite, детерминированный порядок); `dense_leg` переходит на него и теряет параметр `cap`;
  doc-комментарий `embeddings_for_subject_kind` получает предупреждение либо функция удаляется,
  если других вызывающих нет.
- **Не в scope:** нормализация; изменение fusion, порядка и формата ответа.
- **Тесты:** regression — в кэше 2N memory-строк, кандидатов N, кандидат с максимальным
  `subject_hash` обязан быть отранжирован (тест обязан падать на текущем коде); границы чанкования
  (>999 и >1998 кандидатов); поведение не изменилось, когда строк ровно столько же, сколько
  кандидатов; повреждённая строка по-прежнему пропускается поэлементно.
- **Приёмка:** regression-тест красный до правки и зелёный после; строка `D-067` переведена в
  `resolved`.

## D-069 — Детерминированный отказ apply уходит в дедлеттер, а не крутит модель вечно

- **Зависит от:** `T21-00` (только регистрацией строки в `DEVIATIONS.md`). Ортогональна остальным
  карточкам группы: трогает consolidation-раннер, а не нормализацию.
- **Спецификация:** spec 08 §4 (шаги 4–5 и as-built заметки T14-07/D-047/D-050/D-051); spec 04 §4
  (`stale_runs`/`retry_run`, аренда); spec 12 §4 (вывод модели — недоверенные данные).
- **Результат:** окно, чей ответ роутера содержит повторённый `observation_id`, применяется с
  первой попытки; любой детерминированно воспроизводимый отказ apply уходит в дедлеттер за
  ограниченное число попыток, а не крутит локальную модель бесконечно.
- **В scope:** дедупликация `evidence_observation_ids` с сохранением порядка внутри `apply_run` для
  обеих веток (`ProposeCandidate`, `runner.rs:359-384`; `Materialize` через `resolve_evidence`,
  `runner.rs:253-288`) — store-примитивы `propose_candidate`/`insert_candidate_evidence` при этом
  не меняются; `RunOutcomeError::Write(WriteError::Sqlite(_))` с нарушением constraint'а
  классифицируется `Mechanical`, а не `Transient` (`runner.rs:705-721`); потолок для `Transient` —
  N подряд одинаковых `last_failure_fingerprint` уводят ран в дедлеттер; as-built правка заметки
  D-050 в `docs/specification/08-memory.md` §4.
- **Не в scope:** нормализация текста и вся остальная группа 21; промпт и поведение роутера;
  churn индексации; уровни логирования; ретеншн поколений.
- **Тесты:** regression — роутер отдаёт `ProposeCandidate` с дважды повторённым `observation_id`
  ⇒ `run_once` = `Applied`, в `candidate_evidence` ровно одна строка (тест обязан падать на
  текущем коде); то же для `Materialize` против `memory_evidence`; classification — constraint-
  нарушение из write-транзакции ⇒ `FailureKind::Mechanical`, `next_retry_at` не выставляется,
  `stale_runs` при том же `BUILD_ID` ран не возвращает; страховка — N подряд одинаковых
  транзиентных fingerprint'ов ⇒ ран перестаёт быть retry-eligible; идемпотентность — повторный
  apply того же окна не создаёт вторую строку evidence.
- **Приёмка:** regression-тесты красные до правки и зелёные после; на живом сторе владельца ран
  `01a01648-…` применяется с первой попытки после рестарта демона, и за 10 минут в
  `logs/daemon.<дата>.log` нет ни одной строки `consolidation resume run … failed`; строка `D-069`
  в `DEVIATIONS.md` переведена в `resolved`.
- **Приёмка на живом сторе — отложена решением владельца (2026-08-19):** демон в этой итерации не
  поднимался и продакшн-бинарь не пересобирался, поэтому живая половина приёмки не выполнена. Ран
  `01a01648-42b3-797d-bebb-3e6cba2bf7a5` (сессия `10c0ce45-…`, окно `26115..26117`) остаётся
  запаркован с fingerprint'ом `0.0.0-76-gb14fb3a`; первая же пересборка продакшн-бинаря даёт ему
  ровно одну попытку, которая и будет живым подтверждением. Кодовая половина приёмки
  (красные-до/зелёные-после regression-тесты) выполнена полностью.

## T21-01 — Схема v14 `memory_text_normalization` + репозиторные операции

- **Зависит от:** `T21-00`.
- **Спецификация:** spec 03 §2.5 (`[SPEC]`-амендмент — новая таблица, прецедент X-006);
  spec 13 §3; `crates/store/src/migrate/mod.rs:189-215` (текущий максимум версии — 13).
- **Результат:** миграция 14 и модуль `crates/store/src/memory/normalization.rs` без единого
  потребителя.
- **В scope:** DDL (`memory_id` PK с FK `ON DELETE CASCADE`, `status IN ('ready','skipped','failed')`,
  `source_text_sha256`, `normalized_text`, `source_language`, провенанс — `normalizer_model_id`,
  `prompt_version`, `normalizer_version`, `attempt_count`, `last_error`, `next_attempt_at`,
  `created_at`, `updated_at`, `CHECK ((status='ready') = (normalized_text IS NOT NULL))`, индекс по
  `(status, next_attempt_at)`); регистрация в `ALL` + абзац в его doc-комментарии;
  `upsert_normalization` с условным UPDATE-сторожем по текущему тексту, `normalization_for`,
  `entries_needing_normalization`, `normalization_counts`, `delete_normalization`; константы
  `CURRENT_NORMALIZER_VERSION`, `MAX_NORMALIZATION_ATTEMPTS`; backoff через существующий
  `transient_backoff_delay_ms` (второй кривой не заводить).
- **Не в scope:** эффективный текст и любые изменения ридеров (`T21-02`); переводчик; демон.
- **Тесты:** миграция на свежем сторе и на реальном v13; чексумма заморожена; список версий в
  `crates/store/tests/migrate.rs` обновлён (13 → 14); FK отвергает неизвестный `memory_id` и
  откатывает транзакцию; каскад убирает строку; CHECK отвергает `ready` без текста, не-`ready` с
  текстом и неизвестный `status`; `upsert` идемпотентен; `upsert` отказывает при уехавшем тексте и
  ничего не пишет; предикат/порядок/лимит очереди (терминальные не попадают, `failed` до
  `next_attempt_at` не попадает, устаревший `normalizer_version` попадает); `schema_audit` зелёный.
- **Приёмка:** `cargo test -p local-rag-store --test migrate --test migrate_fixtures --test memory`
  зелёные; `local-rag doctor` на апгрейженном сторе показывает store_version 14.

## T21-02 — `EffectiveText`: единственная точка хэширования memory-субъекта

- **Зависит от:** `T21-01`.
- **Спецификация:** spec 03 §1.2/§4.2; spec 08 §6; spec 10 §3 (as-built: аргумент subject-функции
  memory — эффективный текст).
- **Результат:** вычислить memory-субъект вне одного модуля структурно невозможно; оба ридера
  получают текст и его нормализацию одним стейтментом.
- **В scope:** модуль `crates/store/src/memory/effective_text.rs` (тип с приватным полем и без
  публичного конструктора, общие константы SQL-джойна и колонок, общий маппер строки, чистая
  табличная `decide`, `memory_entry_subject_hash(&EffectiveText)`); `all_memory_entries_with_text`
  → `…_with_effective_text`; джойн в `recall_candidates_for_scope`/`recall_candidate_by_id` и поле
  `RecallCandidate.embed_text` (поле `text` остаётся оригиналом — показ, лексика, бюджет);
  механические правки `subjects.rs:270`, `backfill.rs:703`, `dense.rs:211`; doc-комментарий
  `subject_memory_entry` («для хранимой записи — только через `memory_entry_subject_hash`»).
- **Не в scope:** лексическая нога; фоновый таск; любые записи в новую таблицу.
- **Тесты:** табличный тест `decide` по всем случаям (нет строки / хэш сошёлся / хэш не сошёлся /
  `skipped` / `failed` / перевод из пробелов / терминальная запись); parity-тест
  `crates/store/tests/memory_normalization_parity.rs` — множество хэшей из
  `memory_entry_subject_keys` против множества из `recall_candidates_for_scope` (включение,
  побайтовое равенство, отсутствие фан-аута, сохранённый `ORDER BY memory_id`); lint-тест
  `crates/store/tests/memory_subject_lint.rs` — `subject_memory_entry` встречается в непроверочном
  коде ровно в двух файлах; существующие тесты `subjects`/`backfill`/`dense` зелёные без ослабления
  ассертов.
- **Приёмка:** `cargo test -p local-rag-store -p local-rag-embed -p local-rag-memory` зелёные;
  факт «вызов `subject_memory_entry` из `crates/memory` не компилируется» зафиксирован в evidence.

## T21-03 — Детерминированный детектор письменности

- **Зависит от:** `T21-00`.
- **Спецификация:** ADR-0010 §Decision 8/§Consequences (заявленное ограничение).
- **Результат:** `crates/memory/src/normalize/detect.rs` — чистые `script_class`/`script_stats`,
  без модели, сети и состояния.
- **В scope:** снятие нейтрального шума (fenced/inline код, URL/email/пути, uuid/hex/base64-подобные
  токены, идентификаторы с `_`/`::`/внутренней заглавной/`()`, цифры и пунктуация); NFD с
  отбрасыванием combining marks; счёт латиницы против не-латиницы по алфавитным символам; две
  именованные константы (`MIN_ALPHABETIC_CHARS`, `NON_LATIN_RATIO`) с обоснованием в doc; явное
  заявленное ограничение «различаем письменности, не языки» в doc-комментарии модуля.
- **Не в scope:** любая интеграция; определение конкретного языка; n-gram/ML-модели.
- **Тесты:** табличная фикстура ≥30 строк (ru/en проза; код-свитч «проза + идентификаторы + путь»;
  чистый код; только URL/uuid; строки короче порога; de/fr/pl → `English` с комментарием
  «declared limitation»; CJK/арабский/иврит; эмодзи; пусто); по именованному тесту на каждую
  константу с граничным входом; диакритика (`é`, `ü`, `ł`) считается латиницей; идемпотентность;
  отсутствие паники на всех строках `fixtures/memory-recall/corpus.json`.
- **Приёмка:** таблица ожиданий воспроизводится тестом один-в-один; ограничение присутствует в doc
  дословно.

## T21-04 — Компонент перевода

- **Зависит от:** `T21-03`.
- **Спецификация:** spec 08 §4 `[FIXED]` (`local_only`); spec 10 §1; spec 12 §4 п.5 (adversarial);
  ADR-0006; уроки D-050/D-057.
- **Результат:** `crates/memory/src/normalize/translate.rs` — `translate(pool, policy, req)`, чистая
  `validate`, `classify_translate_failure`, `TRANSLATOR_VERSION`, типизированные ошибки.
- **В scope:** короткое замыкание passthrough по детектору (ноль вызовов генератора); промпт сырой
  строкой по образцу `crates/memory/src/prompt.rs:27` с четырьмя few-shot примерами, один из
  которых — инъекционный payload, переведённый как инертный текст; user-сообщение сериализуется
  serde как `{"src": …}`; ответ — одна строка `{"en": …}` с `deny_unknown_fields`; валидация
  (`FinishReason::Length` → `Truncated` до разбора, снятие markdown-fence через существующий
  `parse::strip_markdown_fence`, полоса длины относительно источника, скриптовая проверка выхода,
  жёсткий байтовый потолок без молчаливого усечения); `max_tokens` от `estimate_tokens` источника с
  потолком; pre-flight по длине входа; классификация mechanical/transient/`Unavailable`.
- **Не в scope:** chunked-перевод длинных записей (явно, с обоснованием в doc); любая запись в БД;
  фоновый таск; перевод запроса.
- **Тесты** (на `ScriptedGenerator`, без реальной модели): happy path ru→en; ответ в fence; валидный
  префикс + мусорный хвост; пустой/пробельный ответ → `Refused`; `FinishReason::Length` →

## D-075 — [РЕШЕНИЕ ВЛАДЕЛЬЦА] Нормализация хранимого текста не двигает метрику: разрыв в слиянии, а не в эмбеддинге

- **Зависит от:** `T21-09` (измерение уже есть).
- **Спецификация:** spec 08 §6 (`relevance: RRF(FTS, dense)`); ADR-0010 Decision 1/6; карточка `T21-09`.
- **Найдено:** плотная нога ранжирует ожидаемую запись №1 в **24/24** запросах во **всех** конфигурациях, включая

  1. изменить слияние для memory-recall (например, floor/boost одноногим плотным хитам, или fallback: если плотная
     нога уверенно даёт №1, а лексическая её не видит — не хоронить её ниже топ-5);
  2. дать лексической ноге нормализованный текст — прямой пересмотр ADR-0010 Decision 6 («BM25 raw-against-raw»),
     со своими последствиями для частично нормализованного стора;
  3. считать, что на этом корпусе выигрыш достижим только со стороны запроса, и решать это в `T21-10`;
  4. принять как есть: нормализация остаётся страховкой на будущее, метрика сегодня не растёт.
- **Не в scope до решения:** любые правки fusion/recall «на всякий случай»; изменение корпуса ради лучшего числа.
- **Тесты (после решения):** зависят от выбранной ветки; при (1) — юнит на новое правило слияния плюс повторный
  `memory-recall-bench --config all` с зафиксированными числами до/после.
- **Приёмка:** решение записано в ADR-0010 (новая ревизия или отдельный ADR), `D-075` переведён из `blocked`,
  `G21` может стартовать.

## D-074 — Вектор удалённой записи переживает `purge`

- **Зависит от:** `T21-07` (только регистрацией строки в `DEVIATIONS.md`).
- **Спецификация:** spec 12 §3 `[FIXED]` («`purge` is the only hard-delete path»); spec 08 §3;
  spec 03 §1.4 (кросс-БД транзакции запрещены), §4.2 (`embedding_cache`).
- **Результат:** после `purge` в `cache.sqlite` не остаётся векторов удалённых memory-записей, и
  это наблюдаемо, а не «когда-нибудь вытеснится».
- **В scope:** удаление memory-векторов в отдельной транзакции `cache.sqlite` **после** коммита
  state-транзакции purge (порядок как в `T21-05`: state — источник истины, кэш догоняет);
  subject-хэши считаются той же `decide_effective_text`/`memory_entry_subject_hash`, что и путь
  записи, по **обоим** вариантам текста (исходному и нормализованному), потому что запись могла
  быть нормализована; счётчик удалённых векторов в отчёте purge; та же обработка для `purge --all`.
- **Не в scope:** удаление векторов при `retract`/`supersede` (запись остаётся в сторе, это не
  жёсткое удаление); общий сбор осиротевших строк кэша (это работа для отдельного sweep, не для
  privacy-пути); изменение `backfill`.
- **Тесты:** `purge --memory` уносит вектор нормализованной записи и вектор ненормализованной;
  падение между двумя транзакциями оставляет стор консистентным (state уже без записи, повтор
  чистит кэш) — именованный failpoint; `purge --all` оставляет 0 memory-векторов; вектора **чужих**
  записей не трогаются; отчёт считает ровно удалённое.
- **Приёмка:** тесты зелёные; структурно ни одной кросс-БД транзакции; `DEVIATIONS.md` `D-074` →
  `resolved`.

## Фаза 2 — English-canon (решения владельца, 2026-08-20)

Ревизия `T21-09`/`D-075` показала, что фаза 1 реализовала **не ту** интервенцию, которую измеряла:
`store_en` в харнессе подменяет `memory_entry.text` целиком, то есть кормит английским **обе** ноги
(`crates/xtask/src/memory_recall_bench/run.rs:197-198`), а ADR-0010 Decision 1/6 сознательно
оставили канон и BM25 нетронутыми — то есть перевели только плотную ногу, которая и без перевода
брала rank-1 в 24/24. Отсюда `pipeline_en` = `baseline` запрос в запрос.

Владелец назвал задуманное: нормализация **на границе сервиса** — вход проверяется на язык,
не английский переводится, дальше сервис работает с ним как с английским. Три решения:

1. **Английский — канон.** `memory_entry.text` хранит английский; оригинал уходит в провенанс.
2. **Охват — память и дескрипшены к коду.** `code_raw` не трогаем (перевод кода уничтожил бы
   точный лексический матч). Description-нога — отложенный post-v0 scope (`docs/idea.md:688`,
   spec 09 §4), поэтому правило для неё записывается нормативно, а кода под неё в этой волне нет.
   **Владелец сформулировал это как «явно указать агенту использовать английский язык для
   написания дескрипшнов».** Поправка 2026-08-20: при первичной регистрации фазы 2 это обещание
   осталось в преамбуле и **не получило карточки-владельца** — ни одна карточка `T21-11…T21-18`
   его не объявляла, то есть требование выпало из реестра, хотя и не было заявлено выполненным.
   Пункт закреплён за `T21-12`.
3. **Сначала просить английский в описаниях инструментов.** Самый дешёвый рычаг не был тронут:
   `SERVER_INSTRUCTIONS` не говорит про язык ни слова, у `remember.text` нет описания вообще.
   Строка в описании стоит ноль инференса и работает на источнике; переводчик стоит ~секунду
   локального GPU на запись и работает на следствии.
4. **Запросы `search_code` нормализуются тоже** (решение 2026-08-20, уточняющее пункт 2).
   Изначально владелец сказал «каждый инпут-запрос», а при регистрации фазы 2 кодовый поиск был
   исключён — это было решение исполнителя, не владельца, и оно отменено. Основание не
   косметическое: `code_raw` индексируется дословно, поэтому русский запрос к коду **никогда** не
   матчится в BM25, работает только плотная нога — ровно та асимметрия, из-за которой провалилась
   фаза 1, только в другом пилларе. Карточка — `T21-19`, после `T21-15` и на его компонентах.
5. **Наблюдения и evidence остаются дословными** (решение 2026-08-20; при первичной регистрации
   фазы 2 не было адресовано вовсе — ни «переводим», ни «оставляем»). То, что пишут хуки и
   `give_feedback`, — это запись того, что действительно было сказано; перевод превратил бы её в
   пересказ и обесценил `inspect_memory_evidence` (spec 12 §3). Противоречия с «сервис работает с
   инпутом как с английским» нет: роутер после `T21-11` пишет `text` по-английски независимо от
   языка наблюдений, поэтому durable-запись всё равно выходит английской. Правило действует там,
   где в нём смысл (память и поиск), и не действует там, где смысл — дословность (доказательная
   база). Записывается в ADR-0011 как явная граница охвата, а не как умолчание.

Следствие для объёма: английский канон **вычитает** код. `effective_text.rs`, порядок
«вектор → строка» в `normalization/write.rs`, двойное хэширование и lint-тест существуют ровно
потому, что канон нельзя было менять; снятие ограничения убирает их вместе с дефектом вечных
осиротевших векторов. Правка `lexical.rs` не нужна: нога читает канон, а он теперь английский.

Порядок фазы 2: `T21-11` (контракт на английский) → `T21-12` (ADR-0011 и ревизия нормативных
текстов) → `T21-13` (схема v15, снос двойного текста) → `T21-14` (write-граница) →
`T21-15` (query-граница памяти, заменяет `T21-10`) → `T21-19` (query-граница кодового поиска) →
`T21-16` (устойчивый переводчик) → `T21-17` (backfill существующих) →
`T21-18` (непасыщенный корпус и перемер) → `D-074` → `G21`.

## T21-11 — Английский по контракту: инструкции, описания инструментов, промпт роутера

- **Зависит от:** `T21-09` (его результат — основание фазы 2).
- **Спецификация:** spec 11 §2 as-built T19-01 (`[SPEC]`: бюджет каталога `MAX_CATALOG_BYTES`,
  триггерные первые предложения, deferred-loading порог); spec 11 §2 `instructions` («server
  instructions describe search protocol»); spec 14 §1 item 4 `[FIXED]` — планка про **вход**
  (RU/EN-транскрипты) и ожидаемые **op_kinds**, не про язык выходного текста; ADR-0010 Decision 11.
- **Результат:** ни одна поверхность больше не просит агента писать durable-память на языке
  наблюдения; объём оставшегося перевода становится измеримым, а не предполагаемым.
- **В scope:**
  - абзац про язык в `SERVER_INSTRUCTIONS` (`crates/local-rag/src/daemon/mcp/instructions.rs`):
    durable-память ведётся по-английски, `remember` пишется по-английски, `recall` спрашивается
    по-английски, идентификаторы/пути/хэши/цитаты кода остаются дословными;
  - описание поля `remember.text` (`tools.rs`), которого сегодня нет вообще, плюс та же оговорка
    у `recall.query` и `edit_memory.patch.text` — коротко, потому что каждый байт каталога
    конкурирует с порогом deferred-loading (spec 11 §2 as-built T19-01);
  - правило вывода в промпте роутера (`crates/memory/src/prompt.rs`): `text` пишется по-английски
    независимо от языка наблюдений, идентификаторы и цитаты дословно; правится и абзац
    модульного doc'а, который сегодня утверждает обратное;
  - `MemoryConfig.normalize_to_english` → `false` (`crates/core/src/config/mod.rs`) и остановка
    старого воркера: он тратит локальный GPU по схеме, которую `T21-13` снесёт; правка as-built
    заметки ADR-0010 Decision 11 с явной ссылкой на `D-075` как основание.
- **Не в scope:** любая правка канона, схемы, ридеров и путей записи (`T21-13`/`T21-14`);
  перевод запроса (`T21-15`); удаление переводчика или его машинерии; ADR-0011 (`T21-12`);
  правки `[FIXED]`-текста.
- **Тесты:** `SERVER_INSTRUCTIONS` называет английский и оговорку про дословные идентификаторы;
  у `remember.text`/`recall.query`/`edit_memory.patch.text` есть непустое описание, называющее
  английский; сериализованный каталог по-прежнему под `MAX_CATALOG_BYTES` (тест уже есть —
  зафиксировать новый размер в evidence); системный промпт роутера содержит правило языка;
  golden-тесты промпта обновлены; 42 фикстуры `memory.router.op.*` зелёные без ослабления
  (они проверяют `op_kinds`, не язык — это и есть доказательство, что `[FIXED]` 14 §1 цел);
  дефолт конфига `false`, round-trip, частичная секция `[memory]` его не сбрасывает.
- **Приёмка:** `cargo test -p local-rag -p local-rag-core -p local-rag-memory` зелёные;
  `cargo xtask memory-bench` без регрессии op-точности; на живом сторе после рестарта демона в
  `memory_text_normalization` не появляется новых строк и в логе нет строк нормализации.
- **Приёмка измерением (отложенная, записывается в evidence позже):** через неделю работы
  `local-rag stats --json | jq '.memory.normalization'` — доля `skipped` против `ready` и есть
  ответ, сколько переводческой страховки нужно дальше. Поверхность существует с `T21-08`.
- **Приёмка на живом сторе — отложена (2026-08-20):** демон владельца (`pid 96425`) обслуживает в
  том числе идущую сессию, а рестарт требует пересборки release-бинаря и рвёт MCP-соединение, — то
  есть заметное вмешательство в рабочее окружение, а не проверка. Состояние снято **чтением**:
  `memory_text_normalization` = `skipped 98` / `ready 15` / `failed 4`. Дефолт `false` вступит в
  силу при ближайшей пересборке и рестарте, которые владелец делает сам; кодовая половина приёмки
  (тесты, бенч, линт) выполнена полностью. Отдельно зафиксировано как сигнал: дедлеттеров стало
  **четыре** (в `T21-08` их было три), то есть `local-rag doctor` на живом сторе прямо сейчас
  возвращает `exit 1`, и снять это состояние нечем. Решение владельца 2026-08-20: отдельной
  девиации не заводить — эти строки перевыпускает `T21-16` подъёмом `CURRENT_NORMALIZER_VERSION`,
  и та же карточка решает судьбу самого exit-кода.

## T21-12 — ADR-0011: английский канон, ревизия нормативных текстов

- **Зависит от:** `T21-11`.
- **Спецификация:** spec 08 §3 `[FIXED]`; ADR-0010 Decisions 1/3/6/11; `D-075`.
- **Результат:** английский канон — оформленная ревизия дизайна, а не правка по ходу.
- **В scope:** `docs/adr/0011-english-canon-for-durable-memory.md`, супэрсидящий ADR-0010
  Decisions 1/3/6; амендменты spec 08 §3 (канон английский; правка текста системным актором
  разрешена и обязана иметь audit-запись), 08 §6, 10 §3, 11 §6, 12 §3 (оригинал остаётся в
  выгрузке владельца); `D-075` из `blocked` в `resolved` с указанием, каким решением закрыт;
  `TRACEABILITY.md`. Плюс **три границы охвата**, которые ADR обязан назвать поимённо, потому что
  каждая из них — решение владельца, а не умолчание:
  - **дескрипшены к коду генерируются и хранятся на английском**, и промпт их генератора просит
    английский так же, как это теперь делает промпт роутера (`crates/memory/src/prompt.rs`,
    `T21-11`). Description-нога (`structural_description`, режим `semantic`) — отложенный post-v0
    scope (`docs/idea.md:688`, spec 09 §4 / 11 §1), поэтому правило записывается в ADR-0011 и в
    spec 09/10 **нормативно**, а кода под неё в этой волне нет: его исполняет тот, кто будет её
    строить. Это тот самый пункт, который выпал из реестра при первичной регистрации фазы 2 (см.
    поправку к решению 2 в преамбуле);
  - **`code_raw` остаётся дословным** — перевод кода уничтожил бы точный лексический матч по
    идентификаторам, ради которого лексическая нога и существует;
  - **наблюдения и evidence остаются дословными** (решение 5 преамбулы) с обоснованием: evidence —
    запись сказанного, а не пересказ; durable-запись всё равно выходит английской через роутер.
- **Уточнено разведкой нормативных текстов при исполнении (2026-08-20)** — карточка называла
  адреса приблизительно:
  - **08 §3 ломается меньше, чем считалось.** `[FIXED]` уже говорит, что текст меняется **только**
    через `edit` с новым `entry_version` и audit-строкой; инвариант «в итоге английский» этот
    контракт **использует**, а не нарушает. Амендмент узкий: третий актор (`system`, в коде
    `Actor::System` уже есть) плюс новая строка про язык.
  - **08 §6 правится не там, где ждали.** Строка `RRF( FTS over memory text , … )` при английском
    каноне остаётся дословно верной — обе ноги читают один и тот же `memory_entry.text`. Амендмент
    нужен диаграмме конвейера: новая стадия нормализации **запроса**. Симметрично — `09 §1`.
  - **`remember` живёт в 11 §2, а не в §6.** §6 — это CLI (`inspect`/`export`/`purge`); контракт
    инструмента и его as-built заметки — в §2.
  - **As-built заметки фазы 1 пересматривает не эта карточка.** Их владельцы — те, кто меняет код:
    `03 §2.5` (T21-01), `10:249` (T21-02), `10:325` (T21-05), `12:173` (T21-07), `02:584` (T21-06)
    → `T21-13`; `11:1014` (T21-08, гейт `doctor`) → `T21-16`. `08:513` (T21-09) и `11:425` (T21-11)
    остаются: это свидетельства, а не проект.
- **Не в scope:** любой код; пересмотр as-built заметок фазы 1.
- **Тесты:** нет; проверка резолвимости ссылок ADR (`cargo test -p xtask --test adr_links`).
- **Приёмка:** перечисленные файлы внутренне непротиворечивы; каждое решение владельца от
  2026-08-20 присутствует в ADR-0011 поимённо; `D-075` `resolved`; ни один `[FIXED]`-текст не
  изменён без явной ссылки на ADR-0011 как основание; ни одна карточка `T21-13+` не считается
  начатой до этого.

## T21-13 — Схема v15: провенанс оригинала, снос двойного текста

- **Зависит от:** `T21-12`.
- **Спецификация:** ADR-0011; spec 03 §2.5; spec 13 §3.
- **Результат:** у записи снова **один** текст, и он английский.
- **В scope:** миграция 15 — `memory_text_normalization` становится провенансом оригинала
  (`source_text`, `source_language`, `translator_*`, `translated_at`), `memory_entry.text` —
  канон; удаление `crates/store/src/memory/effective_text.rs`, `NORMALIZATION_JOIN`, двойного
  хэширования в `subjects.rs`/`backfill.rs`/`dense.rs`, lint-теста и
  `crates/local-rag/src/daemon/normalization/write.rs`; `crates/store` остаётся без генератора
  (прецедент D-063).
- **Судьба ретрай-колонок решается явно, а не как получится.** Дедлеттер сегодня считается по
  `status='failed' AND attempt_count >= MAX_NORMALIZATION_ATTEMPTS`
  (`crates/store/src/memory/normalization.rs:478-481`), и на этом числе висит exit-код `doctor`
  (`crates/local-rag/src/cli/doctor.rs:302-305`). Инвариант `T21-14` — «в итоге английский» —
  очередь и отказы сохраняет, поэтому `status`/`attempt_count`/`next_attempt_at`/`last_error` и
  читатели `normalization_backlog`/`dead_lettered_normalizations` обязаны быть либо перенесены в
  новую форму таблицы, либо сняты вместе со своими читателями и гейтом. Миграция, которая молча
  оставит их наполовину, оставит и `doctor` красным по колонкам, которых больше нет.
- **Не в scope:** врезка на границах (`T21-14`/`T21-15`); backfill существующих (`T21-17`);
  очистка накопившихся дедлеттеров — их перевыпускает `T21-16` сменой `normalizer_version`.
- **Тесты:** миграция на свежем сторе и на реальном v14; чексуммы заморожены; `schema_audit`
  зелёный; ридеры отдают канон; ни одна кросс-БД транзакция не появилась; `doctor` на
  мигрированном сторе отвечает и его exit-код определён (а не падает на исчезнувшей колонке).
- **Приёмка:** две несовместимые модели текста не сосуществуют в дереве; сальдо строк
  отрицательное и зафиксировано числом.

## T21-14 — Нормализация на write-границе

- **Зависит от:** `T21-13`.
- **Спецификация:** ADR-0011; spec 08 §3; spec 12 §4 (untrusted-вход переводчика).
- **Результат:** запись, созданная не по-английски, ложится в стор английской, а её оригинал —
  в провенанс.
- **В scope:** врезка **выше стора** в двух продовых точках —
  `crates/local-rag/src/daemon/mcp/memory_write.rs` (инструмент `remember`) и
  `crates/store/src/memory/review.rs` + консолидационный раннер (путь роутера): `script_class`
  (бесплатно) → при необходимости `translate` → английский в стор, оригинал в провенанс;
  инвариант **«в итоге английский»** — при отказе перевода запись сохраняется с оригиналом,
  встаёт в очередь, и канон переписывается системным актором (`Actor::System`) с audit-записью.
- **Уточнено при исполнении (2026-08-21):**
  - **адрес роутерной точки в карточке неверен.** `crates/store/src/memory/review.rs` живёт
    **внутри** стора — генератора там нет и быть не должно. Настоящий шов один:
    замыкание `generate` в `crates/local-rag/src/daemon/lifecycle.rs`, которое питает **оба**
    драйвера консолидации сразу и отдаёт типизованный `Vec<GeneratedOp>`;
  - **роутерному пути провенанс не пишется, и это решение, а не упущение.** `commit_apply_run`
    держит транзакцию внутри стора, поэтому внешний вызывающий мог бы записать провенанс только
    **второй** транзакцией, а падение между ними оставило бы английский канон с потерянным
    происхождением. И не надо: текст роутерной записи произвёл наш собственный промпт, а
    подлинные слова автора — наблюдения, и они хранятся дословно (ADR-0011 §Decision 7);
  - **`edit_memory` взят в scope** сверх названных карточкой двух точек: тот же файл, та же
    форма транзакции, тот же текст, входящий в канон;
  - **тест «audit-строка системной правки» перенесён в `T21-17`.** `T21-14` записи только
    создаёт (`remember`, роутер) и правит по явной команде пользователя (`edit_memory`) —
    переписывания чужого канона системным актором здесь нет ни на одном пути.
- **Не в scope:** сторона запроса (`T21-15`); устойчивость переводчика (`T21-16`); свип, ставящий
  канон уже лежащим в очереди записям, и его audit-строка (`T21-17`).
- **Тесты:** английский вход не вызывает генератор **ни разу**; русский вход даёт английский
  канон и провенанс с оригиналом; отказ перевода не теряет заметку и не пишет ложный канон;
  отсутствие модели — отказ, не паника, и **не** тратит попытку записи; повтор с тем же
  `idempotency_key` не переводит второй раз; `edit_memory` заменяет строку, а не оставляет старую;
  op без текста проходит границу побайтово.
- **Приёмка:** латентность `remember` на английском входе зафиксирована числом вместе с ценой
  добавленного детектора; `crates/store` по-прежнему не знает про генератор.

## T21-15 — Нормализация на query-границе памяти (заменяет `T21-10`)

- **Зависит от:** `T21-14`.
- **Спецификация:** ADR-0011 (супэрсидит ADR-0010 Decision 3); spec 08 §6; spec 02 §6.
- **Результат:** не-английский запрос ищет по обеим ногам как английский.
- **В scope:** врезка в `crates/memory/src/recall/pipeline.rs` **до** обеих ног, внутри уже
  существующего per-worktree read-lock'а: детект → перевод → английский текст идёт и в
  `match_expression` (BM25), и в эмбеддинг запроса; кэш переводов запросов по sha256; отказ
  перевода не роняет recall — деградация на оригинал плюс явный маркер в `RecallOutcome`
  (прецедент `dense_degraded`, 02 §6 «nothing degrades silently»).
- **Не в scope:** запросы `search_code` — они **в** охвате фазы 2 (решение владельца 2026-08-20,
  пункт 4 преамбулы), но отдельной карточкой `T21-19`, потому что это другой пиллар и другой
  нормативный раздел (spec 09), а одна итерация — одна карточка. `T21-19` переиспользует детектор,
  переводчик и кэш переводов, введённые здесь.
- **Тесты:** английский запрос не вызывает генератор; русский запрос находит английскую запись,
  и **обе** ноги сообщают хит; повторный запрос в сессии берётся из кэша (ноль вызовов);
  отказ перевода даёт результат по оригиналу и выставленный маркер.
- **Приёмка:** `warm recall p50` для не-английского запроса зафиксирован числом (сегодня 38.6 мс
  на английском); `T21-10` помечен заменённым, а не выполненным.

## T21-19 — Нормализация на query-границе кодового поиска

- **Зависит от:** `T21-15` (переиспользует его детектор, переводчик и кэш переводов запросов).
- **Спецификация:** spec 09 §1/§4/§5 (`[SPEC]`-амендмент: что подаётся ногам); spec 02 §6
  («nothing degrades silently»); ADR-0011.
- **Результат:** не-английский запрос к коду ищет по обеим ногам, а не по одной.
- **Почему это не косметика:** `code_raw` индексируется дословно, поэтому русский запрос
  **никогда** не даёт лексического совпадения — работает только плотная нога. Это ровно та
  асимметрия «одна нога видит один язык, другая другой», из-за которой провалилась фаза 1,
  воспроизведённая в кодовом пилларе.
- **В scope:** нормализация `SearchRequest.query` (`crates/search/src/pipeline.rs:198-202`) —
  единственного поля, из которого обе ноги выводят свой вход (лексическая токенизирует его,
  плотная передаёт в `embed_query`, `pipeline.rs:862`), поэтому врезка ровно одна; детект →
  перевод → английский текст идёт обеим ногам; переиспользование кэша переводов `T21-15`;
  деградация на оригинал с явным маркером в ответе при отказе перевода.
- **Не в scope:** индексируемый текст (`code_raw` дословен, ADR-0011); дескрипшены (post-v0);
  изменение слияния, режимов и формата ответа.
- **Тесты:** английский запрос и запрос-идентификатор не вызывают генератор **ни разу**
  (см. ниже, почему это общий случай); русский запрос находит английский юнит, и **обе** ноги
  сообщают хит; повторный запрос берётся из кэша; отказ перевода даёт результат по оригиналу и
  выставленный маркер; `name_pattern` и `limit` не затронуты.
- **Латентность:** общий случай бесплатен и это структурное свойство, а не надежда. Детектор
  (`crates/memory/src/normalize/detect.rs`) снимает идентификаторы, пути, uuid/hex-подобные токены
  и требует порогов `MIN_ALPHABETIC_CHARS`/`NON_LATIN_RATIO`, поэтому запрос вида
  `register_embedder_representation` классифицируется как английский и инференса не стоит вовсе.
  Платит только запрос, действительно написанный прозой не на латинице.
- **Приёмка:** `warm search p50` для английского запроса не изменился (замер до/после) и отдельно
  зафиксирован числом для не-английского; `[SPEC]`-амендмент к spec 09 на месте.

## T21-16 — Переводчик, выдерживающий длинный текст

- **Зависит от:** `T21-14`.
- **Спецификация:** spec 12 §4 `[FIXED]` (вход и выход модели недоверенные).
- **Результат:** отказ перевода перестаёт быть свойством длины записи.
- **В scope:** снятие однострочного JSON-конверта с **выхода** (он и есть точка отказа: живой
  прогон `T21-08` дал 3 отказа из 18 — `expected ',' or '}' at line 1 column 1136/1892`,
  `invalid escape at column 127`) — сырое завершение со стоп-последовательностью; **вход**
  остаётся JSON-объектом, потому что вход — это защита от инъекций и она работает.
- **Не в scope:** чанкование (отвергнуто ADR-0010 и не переоткрывается).
- **Обязательный побочный эффект — подъём `CURRENT_NORMALIZER_VERSION`.** Это не косметика версии:
  дедлеттер ключуется именно ей, и смена версии перевыпускает **все** строки независимо от статуса
  (`entries_needing_normalization`). Механизм — прямой аналог консолидационного, где дедлеттер
  ключуется `BUILD_ID`, а resume-свип демона (`crates/local-rag/src/daemon/resume/consolidation.rs:184`)
  даёт запаркованному рану ровно одну попытку после пересборки (D-050/D-073). То есть накопившиеся
  дедлеттеры нормализации чинятся **здесь**, а не в `T21-13`.
- **Заодно закрывается exit-код `doctor`.** Сегодня `is_clean()` держит `exit 1` на дедлеттере
  (`crates/local-rag/src/cli/doctor.rs:302-305`), а снять это состояние пользователю нечем: у
  консолидации лекарство наступает само при пересборке, у нормализации — только при смене версии
  нормализатора, то есть при правке кода. Отдельной девиации на это по решению владельца
  (2026-08-20) не заводится: карточка обязана либо дать состоянию путь наружу, либо перестать
  двигать exit-код и печатать дедлеттер как факт — выбор фиксируется в карточке при исполнении.
- **Тесты:** фикстуры — реальные записи владельца, на которых оно падало (красные до, зелёные
  после); adversarial-набор 12 §4 не ослаблен; отказ по-прежнему типизирован и классифицирован;
  подъём `normalizer_version` перевыпускает строку, стоявшую на потолке попыток.
- **Приёмка:** доля отказов на корпусе реальных длин зафиксирована числом до и после; на живом
  сторе владельца четыре дедлеттера (замер 2026-08-20) либо переводятся, либо названы поимённо с
  новой причиной, и `local-rag doctor` возвращает определённый, обоснованный exit-код.

## T21-17 — Backfill существующих записей

- **Зависит от:** `T21-16`.
- **Спецификация:** ADR-0011; spec 08 §3 (audit).
- **Результат:** стор владельца целиком в английском каноне, оригиналы сохранены.
- **В scope:** one-time проход по нетерминальным записям: перевод, переписывание канона
  системным audit-edit'ом, оригинал в провенанс; идемпотентность, возобновляемость, dead-letter
  той же формы; постоянный воркер после этого простаивает.
- **Не в scope:** терминальные записи (`superseded`/`retracted` — их текст исторический).
- **Тесты:** повторный запуск не создаёт вторых правок; прерывание посередине сходится;
  запись, чей перевод отказал, остаётся с оригиналом и попадает в отчёт.
- **Приёмка:** на живом сторе — `stats` показывает ноль отстающих, число переписанных записей
  и число отказов названы поимённо.

## T21-18 — Непасыщенный корпус и честный перемер

- **Зависит от:** `T21-15`, `T21-17`.
- **Спецификация:** spec 14 §7; `D-068`.
- **Результат:** решение про язык впервые опирается на корпус, который способен его проверить.
- **В scope:** расширение `fixtures/memory-recall/corpus.json` до размера, где плотная нога
  перестаёт быть насыщенной (сегодня `dense_rank = 1` в 24/24 во **всех** пяти конфигурациях,
  включая `baseline`): сотни записей, тематически близкие соседи, длины как у реальных
  (до 1024+ символов); перегон всех конфигураций на починенном `D-068` харнессе.
- **Не в scope:** изменение метрик и правил судейства.
- **Тесты:** харнесс детерминирован (повтор даёт побайтово тот же отчёт).
- **Приёмка:** «английский канон + английский запрос» обходит `baseline` во всех кросс-языковых
  парах без регрессии на одноязычных; насыщенность плотной ноги на новом корпусе больше не 100%.

## G21 — Сверка English normalization

- **Зависит от:** `T21-00…T21-19` и все девиации группы в статусе `resolved`.
- **Результат:** `PASS` / `PASS after D-NNN` / `BLOCKED` в таблице Gate results.
- **В scope:** трейс `требование → код → тест` по spec 03 §1.4/§2.5, 08 §3/§4/§6, 10 §3, 12 §2/§4;
